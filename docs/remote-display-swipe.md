# 多指切换远端屏幕

- 入口：远控内“控 → 屏幕 → 三指切屏”。默认开启，按服务器 + 远端独立保存；关闭不影响原有全屏三指上滑打开键盘。
- 触控屏远控画面内三指左滑切下一屏、右滑切上一屏，按屏幕列表顺序首尾循环。不要求全屏，不修改远端分辨率、窗口或文件。
- 单屏不切换。阈值使用窗口 vp，与屏幕像素密度和远控缩放无关；至少滑动 70 vp，1.5 秒内完成，主方向至少是另一方向的 1.5 倍。首次明显移动锁定方向，三个手指必须同向平行移动。
- 抬起第一指时至多切换一次，剩余触点全部丢弃直至抬起；400 ms 冷却防止短时间重复切换。第四指、新触点替换、系统取消、超时、斜滑和已开始的双指滚动/捏合均不能触发切屏。开始时取消待发单击并释放已按鼠标键。
- 屏幕数量/所选屏幕在手势中改变、离开前台、断连、画中画拥有画面或弹出其他面板时不执行切屏。切屏复用原生显示器切换接口，立即拒绝时保留原选中屏幕并显示失败提示；受理后显示短暂屏号提示并刷新视频，不承诺远端已返回首帧。
- “屏幕 x / n”提示只有淡入淡出，不截获触摸，不移动/缩放真实画布；离开页面清理定时器。

## 切屏过渡

三指左右切屏改为 300 ms 横向翻页：左滑时旧屏向左移出、新屏从右侧进入；右滑相反，首尾循环仍保留手势方向。菜单选择屏号按索引前后决定方向。顶部、底部功能栏不参与滑动。

切换前从视频 Surface 获取仅内存中的旧屏影像，冻结原画布比例、缩放与平移。实时视频表面始终在原位，不参与动画，也不重建。旧影像加载期间背景透明，实时画面仍可见；收到 Image 解码完成回调后，经过连续两次 ArkUI `onFrame` 回调跨过一次 UI 帧提交，再发送切屏请求。不再依赖 `onIdle`：其仅在帧尾空闲超过 1 ms 时执行，视频繁忙时可能延期，触发超时并跳过动画。此处帧提交边界不是硬件送显确认。移除了原来的 32 ms 固定延时与至少 120 ms 的等待条件。

切屏后要求收帧、呈现计数都有进展，并等待尺寸更新及已有表面重绑定结束，再获取新屏临时影像。新影像先在旧影像背后加载，确认解码和初始位置提交后，两张影像同步滑动；动画结束后再跨过两次正常刷新帧回调移除影像，露出原位的实时画面。该收帧/呈现判定只是视觉就绪判断，不是目标屏首帧的协议确认。

影像不写文件、不上传，结束后释放，最多同时两张。单次捕获限时 160 ms、像素数上限 900 万；图片加载/提交限时 600 ms，视频与布局等待限时 1200 ms，动画完成限时 500 ms。超时或失败直接回到实时画面，不排队、不再次发送已受理的切屏请求，也不在失败后补播迟到的动画。

过渡期间屏蔽画布触摸、实体鼠标及滚轮，释放先前按住的鼠标键并吞掉残留手指抬起，避免在移动中的画面上误点。重复切屏不排队；离开、断连、后台、PC 失焦、窗口尺寸变化与画中画会清理或跳过，过期回调不影响新会话。`display-switch-animation` 记录截图耗时及错误码、旧/新图片解码就绪、帧提交、覆盖层提交、视频准备等待时长、方向、动画开始/结束以及失败所在阶段，不记录影像内容。仅在现有诊断开关开启时同步写入 HiLog，便于不断开会话核对实际是否播放动画。

回归覆盖“有正常刷新但完全没有空闲回调”以及重复回调去重；旧版测试强制同时触发 `onFrame` 和 `onIdle`，未能暴露该问题。参考 [FrameCallback 官方说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/arkts-apis-uicontext-framecallback.md)。

2026-10-26 实机诊断确认另一条动画未启动原因：Image 返回 `loadingStatus=1`，但回调中的快照与 `@State` 读取出的对象引用不同（`matches=false`），600 ms 后进入 `old_image_not_ready`。ArkUI 状态/Builder 对象包装不能用 JavaScript 引用相等判断同一快照。旧、新快照现分别携带本轮 epoch 与角色，以数值/布尔身份匹配回调；过期轮次和错误角色仍丢弃。测试用不同 Proxy 包装复现修复前失败，并覆盖过期回调、错误回调及重复完成。日志增加实际/预期 epoch，不含画面内容。

## 平台边界

本轮接入应用实际收到的触控屏三指事件，没有把触控板滚轮轴假装成三指事件。当前 SDK 公共定义虽然有 `ThreeFingersSwipe` 数据类型，但本项目可用公共订阅接口没有对应的三指监听入口；`onAxisEvent` 也不提供可靠三指数量。平板/PC 系统导航还可能拦截三指手势，包括触屏。系统未向应用分发时，用“控 → 屏幕”按钮切换；未申请系统级监听权限，也不强占系统三指或四指导航。

参考：[华为 PanGesture](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/ts-basic-gestures-pangesture)、[多设备触屏手势](https://developer.huawei.com/consumer/cn/doc/doccenter-ux-design/hmi-touchscreen-0000001928273206)。触控板支持需后续使用具备公开权限的接口和对应设备验证，不能以类型定义或自动化单测当作已经支持。

## 诊断与验收

`display-swipe` 记录开关恢复/修改、触控来源、屏幕数量、识别方向/原因、持续时间、相对移动量、目标索引和原生返回码，不记录服务器、设备 ID、按键或输入内容；遵循已有诊断开关。

自动化覆盖左右循环、单屏、关闭、全屏上滑、方向锁、捏合/斜滑排除、不同抬手数据格式、四指取消、滚动接续、系统取消、冷却、前后台/断连、屏幕变化、请求失败、鼠标/触控板隔离、偏好恢复以及小窗口/大字体菜单布局。实机仍需分别验证手机、平板和 PC 触屏上的系统手势分发与实际屏幕切换；触控板不属于本轮已验证能力。
