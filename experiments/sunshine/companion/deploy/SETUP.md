# 芝麻远控 · 游戏串流测试套件

这是调试渠道，不是应用市场正式版。Windows 是被串流端；鸿蒙手机、平板、PC／笔记本是观看端。只有**首次安装客户端**可能需要 USB/DevEco，首次配对在同一 Wi-Fi，此后串流、选屏和配对验证不走 USB。不要卸载现有应用、清除配对或覆盖不同签名的正式版。

## Windows x64 助手

1. 解压 Windows 测试包。另从 [Sunshine 官方 v2026.914.233613](https://github.com/SunshineStream/Sunshine/releases/tag/v2026.914.233613) 下载 **Sunshine-Windows-AMD64-lite.zip**，保留原 ZIP。测试套件不捆绑/修改系统已安装的 Sunshine；当前采集路径要求支持 H.264 NVENC 的显卡以及活动桌面。
2. 在解压目录运行（普通用户，不需管理员）：

   `.\Install-CurrentUser.ps1 -SunshineArchive 'D:\Downloads\Sunshine-Windows-AMD64-lite.zip'`

   安装程序核对归档 SHA-256 和程序摘要，保留其他版本及 DPAPI 配对数据。不要开始菜单快捷方式可加 `-NoShortcut`。也可在解压目录运行 `.\SesameStreamCompanion.exe --prepare-sunshine <原ZIP>`，再运行 `.\SesameStreamCompanion.exe --self-check`。预期 `peer_ready=1 capture_ready=1`；关闭旧测试助手后再启动。不要停用日常使用的 Sunshine 来腾端口。
3. 从开始菜单打开 **Sesame Stream (test)**，或运行 `.\SesameStreamCompanion.exe --listen-ip <本机局域网IPv4>`。Sunshine 管理和 RTSP 只监听本机回环，不要映射到公网。新版观看端用已配对的加密控制连接每 12 秒续期，无须每 50 秒重连；任一端退出即停止，长期无应答时回收，单次最多 4 小时。旧观看端不续期，仍按原短会话结束。电脑的播放声音随画面发送，保留本机播放，不使用麦克风；需要静音时用 `--no-audio`。默认不允许键鼠输入，需电脑加 `--allow-input` 并在观看端本次确认。
4. 配对码在**助手本地窗口**显示，仅在三分钟内有效。不要截图公开、发到聊天或写进日志。配对数据在当前 Windows 用户下；只有确认要替换现有配对时才用 `--new-invite`。一个助手身份目前只对应一个观看端。换设备验收时用独立的 `--state-dir <新的空目录>` 和另一监听端口，不要替换原配对。关闭一个助手后再启动另一个。

### Windows 提示“助手已就绪”，手机同一 Wi-Fi 却转公网

独立助手启动时会针对实际监听的网卡检查网络类型，以及当前路径下助手和媒体进程的入站阻止规则。也可运行 `.\SesameStreamCompanion.exe --check-network --listen-ip <本机局域网IPv4>`，只检查，不启动采集或配对。若明确显示阻止，先核对是否为自己信任的专用网络，不必删除配对；未知或没发现显式阻止都不保证端口可达。

先看 Windows 当前网络的配置文件和入站规则。助手成功监听本机端口，不等于防火墙已允许手机访问；此前允许 Python 的规则也不适用于新版 EXE。Windows 可能给新的程序路径创建“公用网络／阻止”规则。安装程序不会自动修改防火墙或把公用网络改成专用。

完整套件附有只读 `Test-LocalNetwork.ps1`：运行 `.\Test-LocalNetwork.ps1 -HelperPath '已安装目录\SesameStreamCompanion.exe'`。它只报告网络类型和当前程序匹配的规则数，不修改系统；没有匹配规则不代表端口一定可达。

- 在已确认可信的**专用局域网**，管理员可在“高级安全 Windows Defender 防火墙 → 入站规则”按**实际安装路径**为 `SesameStreamCompanion.exe` 允许 TCP 47837（自定义端口则填实际值）；为同目录 `sesame_wan_peer.exe` 允许串流 UDP（本地媒体端口动态分配）。两条规则均限专用配置文件、指定手机地址或受信任的本地子网。
- 若同一程序、配置文件和范围已有显式阻止规则，再加允许规则并不能覆盖它。让管理员判断策略，不要关闭防火墙、删除不相关规则、放行整个公用网络或开放 Sunshine 的管理端口。更换助手版本后重新核对程序路径。
- 若当前环境不允许局域网入站且**此前已成功配对**，可以按下面配置公网助手，通过已认证的公网直连或中继工作。首次配对应在允许局域网连接的可信环境完成，不提供跳过配对或校验的方式。

## 鸿蒙观看端

| 设备 | 安装和验证 |
| --- | --- |
| 手机 | 用匹配调试签名、且包含此功能的 HAP 覆盖**同签名调试版**；拒绝覆盖则停止，不卸载。打开「设置 → 游戏串流实验」，从「连接 → 游戏串流」配对。先 Wi-Fi 出画，再用流量看连接信息中的实际路线。 |
| 平板 | 同一 HAP 需要包含该设备的调试授权。在横屏、竖屏依次验证工具栏、三张屏幕卡片、画面比例和触摸命中。不要假设平板有移动数据。 |
| 鸿蒙 PC／笔记本 | 安装针对该设备授权的调试 HAP（非 Windows EXE）。测试窗口调整、最大化、不同窗口比例和选屏。无触屏设备可操作本地菜单；不能据此认定实体键盘、鼠标直通均已验收。 |

同网配对后，链路优先局域网，其次公网 UDP 打洞，网络不可达才自动回退到指定的 UDP 中继。**身份、证书或媒体加密不通过时中止，不降级。** 在「控 → 屏幕」选择当前电脑的一个输出，不改变 Windows 主屏，不同时发送三路画面。旧助手或只有一个真实输出时不显示虚构的多屏。切屏会暂时停止输入，恢复出画后可手动重新授权。HAP 的公网目标仍在调试构建时指定；使用自己的中继须用同一目标重新构建。

## 独立 Linux 中继（可选，单对设备）

1. 需要 Python 3.9+、一个非 root 服务账户以及已开放且空闲的 **UDP 23388**。仅部署在自己授权的独立服务器，不安装到 RustDesk 的 hbbs/hbbr 目录。本套件不自动更改防火墙、不安装系统包。先核验 SSH 主机指纹，配置操作账号的公钥登录。
2. 在该账号下解压 Linux 测试包，运行 `sh install-relay.sh 1800`。只有已知高带宽、并且两端同意时才用 `8000`（单位 kbps，含封装）；不是视频有效码率。该步只写本用户的程序和单元文件，不启动服务。
3. 在成功局域网配对的 Windows 助手目录执行 `.\SesameStreamCompanion.exe --provision-relay user@公网IPv4`。仅经固定主机密钥的 SSH 标准输入发送两份**中继角色票据**；不发送配对原文、TLS 私钥或媒体密钥。首次写入拒绝覆盖；确需更换设备时，停服务、在本地重新配对后再显式加 `--replace-relay-ticket`。
4. 在服务账户执行 `systemctl --user daemon-reload` 和 `systemctl --user start sesame-stream-relay`。未启用用户 systemd 时，可在该用户前台运行 `python3 -I "$HOME/.local/share/sesame-stream-relay/relay_service.py" serve --wire-kbps 1800`。不默认开机启动。Windows 则用 `.\SesameStreamCompanion.exe --broker 公网IPv4:23388`；高带宽实验两端须一致，Windows 再加 `--relay-wire-kbps 8000`。手机仍会先测直连，而不是强制中继。公网默认画面 540p30；旧端、未授权或探测不足时保留低带宽策略。
5. 停止用 `systemctl --user stop sesame-stream-relay` 或在前台按 Ctrl+C。升级保留 `~/.local/state/sesame-stream-relay/roles.bin`；需要撤销授权时先停服务、再单独处置票据，不要删除 Windows 配对目录。首次配对和正常串流都不需要服务器 root 密码。

## 验收边界

测试助手可显式加 `--output-1080p30`，在局域网或公网保持 1920×1080、30 FPS；不改 Windows 的显示模式，不增加票据权限，不提高直连或中继线路上限。1.8 Mbps 线路需为纠错、封装和关键帧留较多余量：若获准 1.4 Mbps 视频预算，1080p 稳定档先请求 0.8 Mbps。高带宽中继为防短队列溢出，仅用超出低带宽基线的视频预算的六分之一提高目标（例如获准 5.8 Mbps 时请求 1.85 Mbps）。持续拥塞仍允许降低码率，但不为小幅回升中断画面，重连时重新探测。即使解码尺寸保持 1080p，低码率下运动画面的清晰度也可能下降。不加此参数时，保留原来的公网 540p30 和局域网自动档。

看连接信息里的**实际路线、实收视频码率、实际 FPS 和连续帧缺口**。探测上限、请求码率、实际载荷不是同一个值。RTT 是网络往返时延，不是从触摸到屏幕显示的总延迟。本机三屏和 USB 测试手机的结果不代替另一台平板或笔记本的实测。

如要专门尝试 1080p60，在 Windows 助手原有启动参数后添加 `--output-1080p60`（与 `--output-1080p30` 二选一）。它明确请求 1920×1080、60 FPS，不改变主屏分辨率、配对或自动选路，也不以复制画面凑帧。公网直连仍有 1.8 Mbps 总上限，高带宽中继仍须两端授权且实际探测通过。弱网档使用较小的视频包，保留原有纠错；高档中继按 16.7 ms 一帧安排发包，不沿用 30 帧档的等待时间。低带宽能显示 1080p 不等于动态画面清晰、也不等于每秒稳定显示 60 个新画面；不加选项时仍为局域网自动、公网 540p30。

60 帧测试档按本次实际预算起步，而非看到“8 Mbps 中继”就请求满额。例如总线路 1.8 / 3.6 / 7.1 Mbps、视频获准 1.4 / 2.85 / 5.65 Mbps 时，起始视频请求分别为 0.50 / 0.95 / 1.80 Mbps，对应媒体包 640 / 768 / 1024 字节。前两档为弱网和中等带宽留更多余量；这三个示例都不是帧率保证。画面专项复测可加 `--no-audio`，平时不必加。
